Packet River 101

A Hands-On Training Syllabus for the Packet River Cyber Range

By Britley Hoff

2026 Edition

The attacks that are actually taking down infrastructure are boring. Not a zero-day, not a nation-state exploit chain. A home router still on admin / admin. A login sent in the clear. A password reused somewhere it should not have been. A message bus that will take an instruction from anyone. String three of those together and you are standing in front of a rail switch.

Packet River is a small town you break into for a high score, and it is built entirely out of those boring attacks. One live map shows the whole place running: traffic cycling through four crossroads, a train on its loop, water and power flowing to the houses, a clean river with people swimming in it. Every building on that map is also a real, deliberately vulnerable service. You scan it and attack it with the same open-source tools you would use on a real engagement, pull the flag hidden inside the exploit, submit it, and watch the town break on screen. Then you hit reset and try again, faster, or quieter.

It is the third in a family with Widgetorium, a vulnerable web-application lab, and Cross Creek, an ICS/OT range. Same idea, learn by doing, except this one keeps score.

How this book is different from the range's own docs

Packet River deliberately does not ship a copy-paste path to owning the town in thirty minutes. This syllabus is the same. Every session below gives you the class of bug, the tool family, the surface to look at, what you will see when it works, and the fix, with its real-world parallel and its MITRE ATT&CK mapping. It does not hand you the exact request, the credential, the parameter, or the flag's hiding place. That tier, the sharp step-by-step, lives in instructor/answer-key.md in the repo, for people running a class. The range also has an opt-in hint that costs points, and hidden notes scattered around the town that cost only the looking.

Standing up the range

Packet River is one docker-compose stack. Every published port binds to 127.0.0.1; start.sh refuses to launch if any port would bind past loopback, and the attacker box has no route off the lab.

cd packetriver
./setup.sh              # preflight, build the images
./start.sh             # bring the town up with the deliberate weaknesses on
./status.sh            # health, the loopback bind audit, the containment probe
./start.sh --segmented # the defended town, for Session 6
./reset.sh             # restore the golden state between cohorts

Then open http://127.0.0.1:8080/, sign up, and start a run. The attacker workstation is a container:

docker compose exec player sh

What it is built from

Polyglot on purpose, so recon and fingerprinting are realistic: PHP/Apache for Main Street, Node/Express for the bank, Python/Flask for the payment gateway and the soft-PLCs, a real CoreDNS server, a real net-snmp agent, real Modbus/TCP, real MQTT, web3270's own TN5250 and TN3270 mocks for the green screens. The game's own pieces, the map server and the scoreboard, stay single-language. The attacker box carries nmap, sqlmap, ffuf, curl, dig, mosquitto-clients, pymodbus, the net-snmp clients, tcpdump, dsniff, and a set of thin Python wrappers under /opt/pktr/scripts.

Authorised use

Use Packet River only: on your own machine; in a lab you control; in a classroom or range where you have permission; under written rules of engagement for authorised training or assessment. Never point a Packet River command, script, payload, scan, or credential at a real system you do not own. Some of these attacks have physical consequences in the real world. This range exists so you never have to learn that on a live one.
